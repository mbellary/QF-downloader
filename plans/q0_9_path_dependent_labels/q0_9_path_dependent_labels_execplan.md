## Task Spec Snapshot (from quant_tasks.md)

### Description

Defines how stop-loss and take-profit outcomes are labeled using path-dependent price behavior, intra-bar extremes, and volatility-scaled barriers.

### Objective

Enable probabilistic modeling of trade outcome distributions, supporting position sizing, risk control, and execution-aware decision-making.

### Purpose

Define probabilistic stop-loss and take-profit outcome labels using full price paths, not point returns.

### Business Use Cases

- Position sizing.
- Risk control.
- Execution logic.
- Expected value modeling.

### Data Providers

Data type required: intrabar highs/lows, volatility-scaled paths.

Approved providers: Dukascopy (intrabar extremes), TrueFX (path realism), Stooq (long-horizon validation).

Relevance: SL/TP modeling must respect true price paths, not close-to-close “fantasy”.

### Example Data & Target

Example: path_high_pips=+6, path_low_pips=-2 with SL=-4 and TP=+5 yields trade_outcome=TP_hit.

### Inputs

The task lists:

- Barrier scaling rules: `/docs/quant/backtest_rules.yaml` (Quant Q0.2)
- Execution constraints: `/docs/quant/execution_constraints.yaml` (Quant Q0.3)

### Global System Constraints

Must comply with the volatility-scaled risk doctrine and regime-aware outcome modeling.

### Barrier Definition

Per entry time $t$:

- $SL = -k_{sl} \cdot \sigma_t$
- $TP = +k_{tp} \cdot \sigma_t$

Barriers are evaluated path-dependently using intrabar extremes.

### Outcome Labels

Label set: {SL_hit, TP_hit, None}. Time-to-event must be recorded.

### Deliverables

A. Normative specification artifacts (Quant-owned):

- `docs/quant/path_outcomes.yaml` MUST encode barrier scaling rules, intrabar path evaluation logic, outcome classes, time-to-event rules, and execution-compatibility constraints.
- `docs/quant/path_outcomes.md` MUST describe economic rationale, why close-to-close labeling is invalid, and relationship to backtest execution rules.

B. Derived artifact contracts (mandatory, downstream):

- `/targets/path_outcomes.parquet` MUST include trade_id, entry_timestamp, SL_level, TP_level, first_barrier_hit, time_to_event, realized_path_extremes.
- `/targets/path_label_metadata.json` MUST include schema_version, horizon definition, barrier multipliers used, volatility source reference, execution compatibility flags.

C. Schema registry entry:

- `/docs/quant/target_schemas/path_outcomes.yaml`
- `/docs/quant/target_schemas/path_outcomes.md`

### Outputs

- `/targets/path_outcomes.parquet`
- `/targets/path_label_metadata.json`
- `/docs/quant/target_schemas/path_outcomes.yaml`
- `/docs/quant/target_schemas/path_outcomes.md`

### Acceptance Criteria

- Intrabar extremes respected.
- No hindsight bias.
- Compatible with backtest execution logic.
- Quant-approved barrier scaling.

## Plan of Work

Write `docs/quant/path_outcomes.md` and `docs/quant/path_outcomes.yaml` such that a downstream implementer can label outcomes deterministically:

- Entry definition (timestamp and price selection).
- Barrier scaling rule (σ-based multipliers) and parameterization.
- Path evaluation logic using intrabar high/low (and what to do if only OHLC is available).
- Horizon definition and time-to-event recording.
- Outcome semantics and any tie-breaking or missing-data rules.

Then create the schema registry entry under `docs/quant/target_schemas/` describing the exact fields and constraints for the derived parquet + metadata JSON.
